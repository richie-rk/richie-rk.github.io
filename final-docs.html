deep-dive · final-docs · post-closing operations

Final Docs: treat an investor as data, not code.

After a mortgage loan closes, PRMI must deliver post-closing document packages to the investor banks that purchased the loans. Trailing documents arrive late, every investor reports exceptions in its own format, and delays put funding lines and regulatory standing at risk. The Final Docs Automation turns that heterogeneous exception data into one consistent picture and reconciles it against custodian records, so the business knows exactly what is missing, where. I owned the architecture and the build end to end.

4 investors onboarded in 1 month· 1 YAML file per investor· reconciled on the PRMI Loan Number· Missing/Defect + Mismatch reports

01 · the problem

Same business concepts, a different format from every investor

Every investor reports final-document exceptions differently: different source files and report locations, different column names for the same business field, different ways of identifying loans, investor-specific document-type vocabulary, and in some cases data that has to be generated from another system rather than read from a file at all. The downstream business process needs exactly one consistent representation.

The original implementation absorbed those differences as branching logic inside a monolith, so every new investor meant 2-4 weeks (two sprints) of bespoke coding and QA. Growth of the investor network was capped by engineering capacity, not by business appetite.

So there were two problems to solve, not one: convert heterogeneous investor data into a unified internal representation, and reconcile it against First American custodian data to identify missing documents and discrepancies.

02 · the architecture

Prepare, persist, reconcile

The system separates four responsibilities. Batch orchestration decides which investors to process. Per-investor processing decides how one investor’s data becomes the common schema. Reconciliation decides what is missing or inconsistent. Reporting decides what the business sees. An Investor Batch Orchestrator loads the YAML configuration and creates one Investor Data Processor per requested investor; every processor runs the same pipeline: load, normalize columns, resolve the PRMI Loan Number where required, assign and standardize document types, persist. The consolidated data lands in the database in the common Final Docs schema, and reconciliation compares it with First American data on the PRMI Loan Number.

03 · configuration over code

What used to be code became configuration

Each investor is described by one YAML file: source directory and report name, a column_map that translates the investor’s column names into the common schema, whether loan-number resolution is required, document-type mappings, and, where needed, the name of a custom processing hook. Illustrative shape, names generalized:

# one file per investor: source, mapping, hooks
Investor-A:
  project_directories:
    report_folders: investor-a/reports
    report_name: exception-report.xlsx
  get_PRMI_loan_number: true
  column_map:
    PRMI Loan Number: Seller Loan Number
    LOAN NUMBER: Investor Loan Number
    BORROWER FIRST: Borrower Name
    Document Type: Document

The processor reverses the configured mapping, renames the incoming DataFrame into the standardized field names, and adds any missing columns as nulls, so the output structure is identical regardless of the input shape. The core modules treat an investor as data, not as hard-wired branches.

04 · configuration-driven dispatch

Custom paths without touching the core

Not every investor can be processed by reading a file. Some need custom data generation: one path builds a second-liens dataset by querying the loan origination system (Encompass) directly and filtering loans on their milestone history. Those paths live in a dispatch table: the YAML names a key, the processor looks up the callable. Illustrative shape:

FD_DATA_FUNCTION_MAP = {
    "Second-Liens": generate_second_liens_data,
    "Investor-B-Document-Types": investor_b_document_types,
    "Investor-C-Document-Types": investor_c_document_types,
}
handler = FD_DATA_FUNCTION_MAP[config_key]   # config names the key
data = handler()

The alternative is the familiar failure mode: if investor A, elif investor B, and a central workflow that grows a branch per counterparty. The registry keeps the central processor stable; adding a custom path means registering a function and naming it in configuration, never editing the dispatch core. Open for extension, closed for modification.

05 · loan identity and document vocabulary

Two normalization problems, solved before reconciliation

  • Loan identity. Some investors report only their own loan number. A resolver queries Encompass with the investor loan number plus the borrower name and recovers the PRMI Loan Number. Ambiguous or empty results are marked unresolved rather than guessed, and surface later in the Mismatch report instead of disappearing.
  • Document vocabulary. Free-text comments are inspected for known keywords to infer a standardized document type, and existing document-type values are normalized through a second mapping, so a dozen spellings of a title policy all become Final Title Insurance. Reconciliation then operates on standardized business terminology, not investor-specific variations.

06 · reconciliation

Every record lands in a category

The consolidated investor data is compared with First American custodian data, joined on the PRMI Loan Number. Findings separate into business categories, and nothing is silently dropped: matched records produce the Missing/Defect findings; investor records whose loan number is absent from the custodian data are reported as mismatches; records whose PRMI Loan Number could not be resolved are called out separately; and duplicate loan-and-document-type combinations are detected and reported.

  • Rerun-safe: same-day duplicates from re-runs are collapsed before reconciliation, earliest record wins, so reprocessing is idempotent.
  • Missing input file: logged and a notification goes out, instead of the run silently proceeding as if the file existed.
  • Custodian data missing for the day: the workflow falls back to the most recent weekly snapshot rather than failing the run.
  • Database failures: logged and re-raised. A write that fails is a run that fails loudly.

The output is an Excel workbook with Missing_Defect, Mismatch and the consolidated investor report plus a summary sheet, and the same findings persisted to the database so downstream systems can consume the results without touching the spreadsheet.

07 · the decisions

Five choices that made it extensible

Configuration over hard-coded investor logic. Adding or changing an investor’s source mapping does not require changes to the core processing workflow.
Separation of orchestration and processing. The batch layer decides which investors to process; the per-investor processor decides how one investor is processed. Each can be tested and reasoned about independently.
Configuration-driven dispatch. Custom processing is registered, not branched into the center, so the central workflow never becomes a pile of investor conditionals.
Common downstream schema. All investor data is normalized before reconciliation, so the reconciliation layer needs no per-investor logic at all.
Database as the processing boundary. Normalized data is persisted before reconciliation, giving the two stages a clean handoff and making intermediate results independently queryable.

08 · impact

Investor expansion at deal speed

Onboarding a new investor fell from 2-4 weeks of bespoke coding to a configuration exercise measured in days: a new YAML file, a few parameter tweaks, and a handler only if the investor needs something genuinely new. In the month after the refactor, four new investors were integrated, work that previously consumed a full quarter of engineering capacity, and the architecture was adopted as the template for two other automation initiatives.
