case-study · max-ai · enterprise rag

MAX AI: grounded answers from the company’s own documents, with citations.

PRMI’s primary knowledge retrieval tool. Mortgage staff ask natural-language questions against guidelines, training and marketing material, and get answers grounded strictly in that corpus, cited back to the source page. I owned the Python backend across all three services: the streaming chat API, the document-ingestion pipeline, and the utility Function App. A colleague owned the React console.

3 Azure services· NDJSON token streaming· 1 search index per project· chunks 1000/100· ada-002 1536-d· GPT-4o at temp 0

01 · the problem

Why retrieval, not a bigger prompt or a fine-tune

A language model’s knowledge is frozen in its weights: a mortgage guideline revised last Tuesday cannot be in them. It has no provenance: an answer is a blend of billions of gradient updates with no pointer back to a source. And when it does not know, it fabricates fluently. For a regulated lender, each of those three is disqualifying on its own. Answers must be current, cited, and able to refuse.

Fine-tuning solves none of this economically. Re-indexing one changed PDF takes seconds; a fine-tune takes hours and a redeploy. Weights cannot point a compliance officer at a source line. Retrieval can be filtered per user at query time; weights cannot be un-learned per user. So the design moves facts out of the model and into a search index, and converts one open-ended generation problem into two smaller, separately debuggable ones: retrieval (did the right chunk surface?) and reading comprehension (did the model use it faithfully?). When an answer is wrong, you can tell which half failed. That separability drives everything below.

02 · the shape of the system

Two halves, opposite performance profiles, one shared contract

Ingestion is throughput-bound: CPU-heavy, tolerant of hours of latency, and it must survive restarts. Chat is latency-bound: almost pure network I/O, stateless, and judged on time to first token. Coupling them into one process would force one set of trade-offs onto both, so they ship as separate deployables: a Durable Functions app with unlimited timeout for the write path, and an always-warm FastAPI service for the read path. A third Function App carries the utility surface: auth, projects, users, session history, feedback.

Provenance, stated plainly: the platform grew out of Microsoft’s open-source RAG reference architecture. The bespoke engineering on top is the HyDE retrieval path, the per-project prompt and index registry, the audit-driven incremental re-index, the multimodal loaders, and the NDJSON streaming protocol with in-band follow-up questions.

03 · the write path

How a PDF becomes searchable chunks with page-level citations

The durable trio. A single HTTP function cannot index a corpus: the work outlives any HTTP timeout, and at scale a crash mid-run is a certainty, not a possibility. Durable Functions splits accept, coordinate, and work. An async HTTP starter validates the request and returns 202 Accepted with a status-polling URL in milliseconds, the asynchronous request-reply pattern. The orchestrator is a replayed Python generator that describes the workflow and nothing else. The activity does all the real work, with the function timeout removed entirely.

  • The per-file pipeline: download and detect encoding, dispatch by file type to the right loader, split into 1,000-character chunks with 100-character overlap that hunt for a clean sentence boundary and keep page provenance, embed with ada-002 into 1,536-dimension vectors, and upsert in batches of 1,000, the API limit.
  • Scanned documents: Azure Document Intelligence extracts text with tables reconstructed as HTML, rows and column spans preserved. For mortgage rate matrices, losing the grid loses the meaning.
  • Idempotent by construction: every file writes a success or failure row to an audit table, and each run starts by reading the successes back and skipping them. The audit table is the checkpoint; a crashed run is resumed by re-invoking the endpoint.
  • Per-file failure isolation: the unit of failure is one document, not the batch. One bad PDF cannot abort a five-thousand-file run, and the exception text is persisted so triage means a query, not grepping logs.
  • The corpus is not just text: every PDF page is rasterized to a PNG so the UI can show the exact cited page. Training videos are frame-sampled with OpenCV, then near-duplicates are dropped by perceptual hashing, so a 40-minute recording yields a handful of distinct slides instead of 72,000 frames. Audio runs through the Azure Speech batch API behind a polling loop.

04 · the read path

Retrieve, ground, stream

Retrieval is hybrid, in three layers. BM25 over a lemmatizing English analyzer catches exact identifiers that embeddings blur: program names, form numbers. An HNSW vector index (1,536-d, cosine) catches paraphrase that keywords miss entirely. A semantic reranker then re-scores the top candidates with a cross-encoder: too expensive for the whole index, affordable for fifty. Recall is stage one’s job; precision is stage two’s.

HyDE is the most interesting trick in the system. Queries and documents sit in different regions of embedding space, not because they differ in meaning but because they differ in register and length: eight words of telegraphic shorthand versus a thousand characters of formal prose. So instead of embedding the question, an LLM drafts a plausible answer and that gets embedded. The draft is wrong on facts but right on form, so its vector lands in the document neighborhood and retrieves the real chunks the fake one imitates. The fabricated text is thrown away; only its position in space is used. It costs one extra completion per question, which is why it is enabled per index rather than globally.

Grounding is a data-formatting decision as much as a prompting one. Each retrieved chunk is prefixed with its own file and page label inside the context window, which is the only reason the model can emit citations like [guide.pdf#page=12]. The system prompt constrains answers to the provided sources and mandates refusal when they do not contain the answer. Generation runs at temperature 0 with a hard token ceiling: for a compliance-facing tool, determinism and a bounded cost per call beat variety.

Streaming is NDJSON: one complete JSON object per line over ordinary chunked HTTP. A single JSON array cannot be parsed until its closing bracket arrives; SSE imposes framing and reconnection semantics this app does not need; WebSockets add a stateful channel for what is a one-shot exchange. NDJSON gives incremental parseability with zero protocol overhead. Frame 0 carries the citations and model metadata before the first token, so the UI paints the sources panel while generation is still in flight. Token frames follow, and the final frame carries suggested follow-up questions, extracted from the stream by a small state machine so its delimiters never leak into the visible answer.

05 · decisions that carried the design

Seven choices, each with a reason

Two deployables, opposite profiles. Batch CPU work and sub-second token streaming do not belong in one process; each half gets the runtime its trade-offs demand.
A container because of OCR. Local PDF partitioning and table extraction in the activity function use the unstructured library, which needs two system installs: poppler to rasterize pages and Tesseract to read them. A standard Function App cannot carry system packages, so the ingestion ships as a Docker image served from Azure Container Registry.
One search index per project. Multi-tenancy by physical isolation, with a project-to-index map in SQL. Simple to reason about, and nothing to filter at query time.
NDJSON with metadata-first framing. Citations arrive before the first token. Perceived latency is the UX metric, and the sources panel is on screen while the model is still writing.
Audit-table checkpointing. State lives in SQL, not process memory, so resume equals re-invoke and progress is inspectable with a query.
HyDE per index, not globally. A real recall win that costs one completion of latency per question, so it is a per-corpus decision instead of a default.
Temperature 0 and a token ceiling. Compliance answers should be reproducible, and every call has a bounded worst-case cost.

06 · what I would build next

The honest roadmap

  • Fan-out/fan-in ingestion: list blobs in the orchestrator and schedule one activity per file with per-file retry, turning a serial hours-long run into parallel work.
  • A retrieval evaluation harness: a labelled question set with recall@k tracking, so chunk size, top-k and HNSW parameters get tuned against measurement instead of anecdote.
  • Structured outputs for the follow-up channel: replace in-band text delimiters with a tool call, so the transport stops depending on the model’s punctuation.
